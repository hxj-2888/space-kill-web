## 三、结论：**自我治疗从未发动**不是缺陷

120 局逐夜观测（`tools/diag-cure-window.cjs`）：

```
外星人被真感染（real）   14 次
被感染后 cureSelf > 0   14 次      ← 额度按时到账
但 req 命中 xenoCure     0 次
branch 已占用          472 / 473    ← 出刀(kill) 或 蛰伏(check)
```

卡明载外星人**四选一互斥**（蛰伏 / 击杀 / 破坏 / 自我治疗）。行动名额被出刀或蛰伏用掉时，
自我治疗本就不该可用 —— 窗口从未打开是**互斥的正确体现**。

**另一件要如实说的**：裁定① 我加在 `engine.js grants` 里的前置条件，在真实对局里
**几乎从不触发**（到账时点「有感染标记」0/473）—— 外星人唯一的感染时点是步骤 7，
而 grants 在步骤 0 之前。额度实际来自 `applyInfection` 里**既有**的那条路径
（真感染即给额度），那条本来就与裁定口径一致。所以裁定① 的口径其实**原本就成立**，
我加的那行是让它显式化、并覆盖「隔夜仍带标记」的情形。

**口径提醒**：以上全部量在**经典席位**下（外星人席位掷出变体 A）。
若掷出变体 B（死囚外星人），局里根本没有经典外星人，
`state.js:137-139` 已注明这是规则的必然结果而非缺陷。因此
「自我治疗在真实席位分布下会不会发动」**尚未量过**，需要先按 §4.1 接入变体再测。

## 六、已知缺陷与待办（**不要重复踩**）

### 6.1 死囚复生表单缺失（既有缺陷，先于 2026-10-08 的裁定批次）

步骤 8 的 `req` 对死囚可推出 `kind='revive'`（6.8.4 复生），但 `form` 首行判
`isClassicXeno(p)`，死囚 `role` 不是 `xeno` ⇒ 落到医生分支返回 `kind='doctor'`，
**`form` 根本没有 `revive` 分支** ⇒ 死囚被静默塞进医生表单（能拿治疗/救援/制药/毒药），
真正的复生无法发动。与 `steps.js` 里 43 号注释描述的外星人那次是同一类病。

- 确定性复现：`node tools/probe-revive-kind.cjs <ROOT>`（非 0 退出 = 缺陷仍在）
- 登记：`IMPL_GAP['convict.revive.form']`
- **未修**，因为修法（给步骤 8 的 form 补 revive 分支）会改死囚行为，需你点头。
- 注意：**在变体接入量测之前（§4.1），死囚根本不上场，所以这个缺陷在任何常规量测里都不会暴露。**

### 6.2 `canActAt` 只认主行动位

`derivation/actions.js` 的 `canActAt(role, step)` → `rolesAt(step)` 按
`actionStep === step` 过滤，**次要行动位对它无效**。船员把 `4a` 加进 `actionSteps` 后，
若 4a 的 `req` 仍用 `canActAt`，声明的 `'4a'` 只落在纸面、派发认不到 —— 那正是「造幽灵步位」。
本轮已改用 `actionSlots`，**下次新增次要行动位时注意同一件事**。

### 6.3 `SKRoleDecl` 没有 `chargeOf` 访问器

`charges` 只能按 `RD.ROLE_DECL[role].charges` 直读（与 `rolesAt` 读 `actionStep` 同一路）。
写了 `RD.chargeOf && RD.chargeOf(...)` 会因 `chargeOf` 为 `undefined` 而**静默短路**，
表现为「该角色永远拿不到窗口」。本轮踩过，靠互斥探针实测 `crewRepair` 命中 0 次才暴露。
⇒ 4a 现在用共享 helper `hasAssistRepair`，`req` 与 `form` 共用，保证判据同源。

### 6.5 观测会扰动随机流 —— 探针必须自证（**本轮最贵的一课**）

`handsover-sim` 的 `AI.decide` 钩子原本会**额外调一次** `V.thought()`，而
`voice.js:468` 的 `COST_HEDGE[cost](g.rng)` 会消费随机流 ⇒ **观测行为改变了 `g.rng` 的序列**，
推演出的对局与裸跑不同源。后果实测可见：同一批种子，扰动版读出 `4a:crewRepair = 1557`，
不扰动的 `classify-dead-surface.cjs` 读出 **1542**；报数区人类胜率也从 69.6% 变回 **68.8%**
（与外部独立测量吻合）。

修法（三处，缺一不可）：
1. **观测期间给 `g.rng` 套一个吞掉所有调用的桩**。mulberry32 的状态藏在 `this.f` 的闭包里，
   复制字段还原不了，只能整体换掉；桩返回值恒定即可，因为我们只取 `thought` 的
   `sense` / `claimKind` 字段，不看 hedge 文案。
2. **自证 rng 中立性**：同一种子在「有钩子」与「无钩子」两种跑法下比对对局指纹
   （胜局/夜次/存活/血量/感染/分支/步位），不一致就报出来并非 0 退出。
3. **自证 `req` 纯净性**：本脚本的 `stepOnce` 钩子会多调一次 `req(g)`，须证明它不返回值也不改状态。

⇒ **判据**：接手任何探针时，先看它有没有「同种子两种跑法比对」这一栏。
没有自证的探针，它的结局数字不可信 —— 它可能只是在量自己的副作用。

## 七、其他工程教训（都是本轮真实踩到的）

1. **钩子要钩在被调用方真正使用的那一层。** `AI.reasoningChain` / `AI.vote` / `AI.applyInfection`
   都是模块内绑定，从导出的门面钩不到 —— 我因此两次得到「全 0」的假读数。
   要钩 `AI.decide`（引擎确实走门面）。**看到全 0 先怀疑钩子，再怀疑实现。**

2. **不要硬编码行号。** 同一批返工里，`setLines(581, [...])` 替换 5 行却漏了第 6 行，
   以及 `at(n)`（1 基）与 `findIndex`（0 基）差一位 —— 两次都造成静默损坏。
   用 `findIndex` + **唯一性校验** + **改后读回校验**。

3. **不要用 CJK 文本做脚本锚点。** 写入工具会改写 `\uXXXX` 与部分 CJK 字符，
   我连续踩到 5 次（连 `\r\n` 转义都被改成真实换行，导致 split 失效、报「找不到明明存在的行」）。
   ⇒ **补丁文本放独立 JSON，脚本只读 JSON**；锚点用 ASCII 正则或码点拼装。

4. **别在注释里写 `*/` 或 U+FFFD 字面量。** 前者提前闭合块注释；后者让「无乱码」校验恒不通过
   （我为说明「原文丢字」写了 3 个替换字符，结果自己被自己的校验拦下）。

5. **混用行尾会制造看不见的损坏。** 往 CRLF 文件插 LF，使两个标签落进同一 `\r\n` 分隔单元；
   随后「只修那一行乱码」的操作替换了整单元，**连带删掉 `js/ai/decide.js` 的 script 标签** ——
   浏览器端整片 AI 静默失效，`node tools/load-order.cjs` 却一切正常。
   ⇒ 改完加载链**必须**核对「标签都在 + 顺序正确 + 标签数未减少」。

6. **随机探针对「潜伏缺陷」不可靠。** `g.rng` 是游戏级共享流，任何取随机次数的变化都会让整条流移位，
   于是同一断言时而红时而绿（死囚O 那条断言后来自己又变绿了）。
   ⇒ 判断「某缺陷是否早已存在」**必须**用确定性探针，并在改动前的 HEAD 上跑同一探针比对。

   6b. **2026-10-08 补：钩子的位置决定读数的时点。** 同一个 `req`，在 `stepOnce` 外层调与在
   引擎内部调，拿到的是**不同时刻**的答案 —— `beginStep` 才把 `g.step` 设成本次步
   （`engine.js:701`），故外层读到的是**上一步**，且时点已在上一步结算之后。
   本批因此误报了四个「死面」（`crew@0.6` / `sheriff@2` / `xeno@5` / `listener@D-report`），
   其中 `sheriff@2` 就是 §4.3 那个「被用掉了却没有窗口」的矛盾 —— **引擎是对的，探针读错了**
   （实测：引擎确实派发 patrol、AI 确实决策、run 确实结算，3 人获得保护）。
   危险特征：错位后的读数**看起来完全合理**（0 次、无异常、不会自己暴露）。
   ⇒ 凡靠「读 `g.step` 再自己调 `req`」取数的探针，必须先证明 `g.step` 已等于本次步。
   本批已在 `handsover-sim` 里加了 `hookMisaligned` 自证栏（三区实测 0），
   并把派发观测改为「按步逐个包住 req 函数本体」（记引擎真实看到的派发）；
   `classify-dead-surface` 的「该步是否被走到」改读 `g.queue[0]`（即将执行的步）。

7. **探针自己的判据错误会伪装成引擎缺陷。** 本轮多次：把「被派发到步骤 2」当成「选了查验」；
   用 `g.phase` 判夜次边界（它在夜末并不翻转）；在 `Engine.stepOnce` 之后读
   `p.repairValue`（刚结算完已清零）或读 `g.decisions`（已被下一步覆盖）。
   ⇒ **探针出「大量违例」时，先怀疑探针**：把每个判据的前提写清楚，再看它是否真的成立。

8. **产物与文档必须对得上。** 破坏率产物一度只有 60 局（241–300），而文档引的是 260 局数字 ——
   等于数字不可复现。已按报数区全量重跑并覆盖产物。
   ⇒ 交接文档里每个数字都要能从落盘产物里读出来。

9. **步序不是升序。** 实序是 `2 → 4b → 3 → 4a → 5 → 6 → 7 → 8 → 9`。
   在 `4b` 检查「4a 是否已结算完」必然得到假残留。
