## 一、批次 44 · 死囚外星人的技能隔离

完整记录见第四十四批交接文档。此处只留三条最容易被后来者重犯的：

1. **「阵营成员 ≠ 能力持有者」。** 死囚**是**外星人阵营成员（参与清场与胜负，判据必须按
   `faction`），但**不持**经典外星人任何技能（判据必须按 `role`）。此前两者被写成同一个
   `faction === 'xeno'`，于是五个席位变体一接进真实对局就整片失守。
   推导层现导出三个判据：`isClassicXeno`（role）/ `isXenoCamp`（faction）/ `isMorphed`。
2. **静默换技能只有一道通用探测器能看见。** 步骤 8 曾派发 `xenoCure` 而 `form` 落到医生分支
   —— 请求与表单 kind 不一致，玩家看到的与引擎解读的是两套技能。门禁 §43 新增：
   **每个步位 `req` 派发的 kind 必须与 `form` 返回的 kind 逐次一致**。
   旧断言跑在 Node 里、从不构造真人表单，所以看不见。
3. **门禁分层有冗余，验门禁必须验门禁。** §43.2 的两处门禁互为冗余，回退任一处都不报警
   （是纵深防御，不是断言失效）。故补了 §43P/Q：构造「已感染且持有额度」的满配死囚，
   直接断言派发侧。

## 四、附件站并入游戏仓

### 为什么做

附件站原先的仓库 `hxj-2888/space-kill` 在 **GitHub 上 404**（已搁置）；Gitee 上的同名仓库是
**另一个项目**（Python 工具，非本项目）。本地克隆的 `origin` 因此指向一个不存在的地址 ——
附件站的改动**长期无处可推**。

这造成了一次真实后果：入库的蒙特卡洛原始 JSON 是**更早一次运行**的数据
（human 3031 / alien 5905 / xeno 1064、617.8s、通道接线 49/506，还留着 C14 / C22 两条已下线通道），
而站点页面是用更新那次的中间产物同步进去的（2951 / 5711 / 1338、717.2s、44/506）。
**JSON 与自己生成的页面对不上。**

> CI 的「重建并比对」只比对 `site/`，看不见 JSON 本身是旧的 —— 这类「门禁只覆盖产物、
> 不覆盖输入」的盲区是本次事故的根因。

### 目录布局（保持原样，`build_site.py` 的路径依赖它）

```
attachment-site/
├─ tools/      生成器（build_site.py / gen_mc_report.py / pdf_to_md.py / inspect_docx.py）
├─ assets/     静态资源（安卓下载二维码）
├─ 剧情/       三条胜利线 docx + 规则 PDF 原件（构建输入）
├─ 公测3.1/    规则 markdown + sim_output/（模拟原始数据与报告）
└─ site/       构建产物 —— 部署的就是这个目录
```

`build_site.py` 用 `ROOT = dirname(dirname(__file__))` 定位根目录，故放在
`attachment-site/tools/` 下即可**原样运行**，无需改任何路径。已实测：重建产出 9 个页面，
与原仓库逐字节一致。

### 顺手修掉的两处

1. **二维码在附件站失效。** 首页「扫码下载应用」卡片点进去返回 HTTP 200 但
   `Content-Type: text/html`（内容是 `<!DOCTYPE html>`）—— Cloudflare 落到 index.html 回退。
   原因是那张图只存在于作品集副本里。
   修法：**移入 `assets/` 作为构建输入**，由 `build_site.py` 复制。
   > 不能只把文件放进 `site/` —— 那会让「产物可由源确定性重建」这道门禁必然失败
   > （build 不生成二维码）。**二进制资源必须由构建产出。**

2. **`build_site.py` 一处归因写错。** 注释写「Windows 上 copy2 覆盖会被占用拒绝」——
   **归因错误**，实为文件带 **ReadOnly 属性**（`os.remove` 对只读文件报 WinError 5）。
   Linux CI 跑在容器里没这个属性，所以从未暴露。清除只读即可重建。

### 未并入的迁出遗留

`公测1.0/`、`公测3.0/`（旧版本门户）—— `build_site.py` 里的 `SRC3` 是**死变量**，
全文从未引用，可证构建不依赖；`.github/workflows/deploy.yml`（对应仓库 404，该工作流
从未真正执行过）。需要保留时复制进 `attachment-site/` 即可。

## 五、跨仓同步 CI（新增 `portfolio/.github/workflows/sync-attachment.yml`）

一次跑完：拉 `space-kill-web/attachment-site`（public）→ CI 内重建并比对 →
部署 `space-kill.pages.dev` → 同步进 `projects/space-kill/` → 提交 → **显式唤起**
`deploy.yml` 上线作品集。触发为每 6 小时轮询 + 手动。**零新 secret。**

### 为什么宿主是 portfolio（决策依据，非偏好）

| 事实 | 值 |
|---|---|
| `space-kill-web` 的 secrets | **无**（一个都没有） |
| `portfolio` 的 secrets | `CF_API_TOKEN` + `CF_ACCOUNT_ID` ✅ |
| 两仓可见性 | 都是 **public** |
| 跨仓**读取**（默认 token） | ✅ 可行（**实测**，非推断） |
| 跨仓**写入** | ❌ 403 —— GitHub 的 `GITHUB_TOKEN` 只能写本仓 |

附件站的**两半**部署都必须写作品集副本，而能写的只有作品集自己；它同时还具备 Cloudflare
凭据 —— 两个条件只有它同时满足。反向（`space-kill-web` 主持）需要额外 3 个 secret。

### ⚠ 三个实测踩到的坑（都不是想出来的）

**1. `GITHUB_TOKEN` 的 push 不触发任何 workflow。**
GitHub 为防止工作流互相触发形成无限递归，刻意如此。后果极其隐蔽：自动提交成功、CI 全绿，
但 `deploy.yml` 根本没被触发、作品集线上不会更新，**且无任何报错**。
> 首次实测时线上副本之所以是对的，只因我此前**手工同步过** —— 属于侥幸，不是机制生效。

**解法**：用 `actions: write` 显式 `workflow_dispatch` 唤起 `deploy.yml`。
链路上「提交」只是留痕，「上线」由这一步负责。

**2. 只比指纹发现不了副本漂移。**
指纹记录的是上次部署的**源**内容。若有人直接改 `projects/space-kill/` 里的副本，
源没变 → 指纹相同 → 判定无事可做 → 漂移永久留存。**与本次事故同类。**

改为两个独立判据：
- **A** 源指纹 vs 上次部署指纹 → 变了才重新部署 Cloudflare
- **B** 本次重建结果 vs 仓库现存副本 → 漂移了就修复

A 假而 B 真时只同步副本、不重复部署（线上内容本就是对的）。

**3. `sparse-checkout` 的模式相对仓库根，不是工作目录。**
配 `path: attachment-src` 时内容落在 `attachment-src/attachment-site/…`。
已在工作流里加 `Assert source layout` 步骤，让这类错误当场报「路径错」而不是在 diff 里
报「产物不一致」。

### 幂等验证

第二次运行全 skipped（源未变、副本无漂移）。端到端验证方式：**故意删掉副本里的二维码**
制造漂移，工作流自动检测 → 从源恢复 → 提交（`8ccd99e`，bot 署名）→ 唤起 `deploy.yml` →
部署成功 → 线上副本 11 个文件与源**逐字节一致**，二维码 1683 字节 HTTP 200。

### 两站边界（勿混）

| | 游戏站 | 附件站 |
|---|---|---|
| 线上 | `space-kill-web.pages.dev` | `space-kill.pages.dev` |
| 源码 | 仓库根 | `attachment-site/` |
| 部署 | `deploy-pages.cjs` / APK | 本 CI |

两站的部署白名单互不重叠，故附件站**不会**被打进 APK、也**不会**出现在游戏站上。
