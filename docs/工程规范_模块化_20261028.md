# 工程规范 · 标准化与模块化（批 ART-0 · 2026-10-28）

> 用户原话：「完成任务后，本项目还有两个方向要做：一个是美术素材对齐；一个是交互体验优化。
> 在这两个方向优化前，**重新做标准化、模块化处理**」。
>
> 本文是那件事的**规矩书**：先把"文件该长什么样、状态归谁、门禁怎么配、素材怎么管"定死，
> 再按批次切代码。两个方向都依赖这份规矩 ——
> 美术对齐要一份**可核对的素材台账**，交互优化要一条**单入口的交互出口**。

## 一、体检（2026-10-28 实测，不是估计）

```
js/ 合计 24,619 行 / 1.66 MB，其中：
  js/engine/steps.js      2466 行（3 个巨型函数）
  js/ui-scene.js          1986 行（61 个函数，一个 IIFE，约 60 个闭包变量）
  js/data/rules.js        1889 行（派生物，勿手改）
  js/ui.js                1814 行（62 个函数，一个 IIFE）
  js/ai/decide.js         1597 行
  js/engine.js            1084 行
```

三个"病"：

1. **单文件过大且状态私有**：`ui-scene.js` 与 `ui.js` 各是一个 IIFE，内部 60 多个变量互相读写，
   想抽任何一个函数都要把状态一起搬。这类文件既是"渲染层"也是"交互层"还兼"状态层"。
2. **门禁跟着文件名走**：`test-ship.cjs` / `test-space.cjs` 里的判据全部写死读 `js/ui-scene.js`
   （`sceneCode`）。**一动文件，20+ 条断言同时失去对象** —— 这是模块化最大的卡口，先解决它。
3. **素材没有台账**：`assets/scene/` 有 `CREDITS.md`（人工维护），但没有机器可核对的清单；
   "哪些素材零引用""哪张图没登记许可"只能靠人眼。

## 二、分层（谁可以读谁）

```
① 数据层      js/data/、js/space.js、js/ship-map.js、js/hud-map.js
              纯数据 + 纯函数，零 DOM、零 global 读取（只写自己的命名空间）
② 规则层      js/v66/**、js/engine*.js、js/state.js
③ 推理层      js/ai/**、js/infer/**、js/corpus/**、js/nlp.js、js/lang/**
④ 视图层      js/ui-scene.js → js/scene/**、js/ui.js → js/ui/**
⑤ 装配层      js/main.js、js/arena.js、js/net.js、js/audio.js
```

**三条铁律**：

- **单向**：①←②←③←④←⑤（箭头 = "可被读"）。反方向读 = 架构破坏，先停下来说明。
- **视图层不得读规则层内部**：只读 `g.phase` / `g.pending` / `View.viewFor()` 的产物（既有红线不变）。
- **可变状态只有一个 owner**（见 §四表）。别的模块要改它，必须走 owner 暴露的方法。

## 三、文件规范

### 3.1 命名

| 类型 | 规则 | 例 |
|---|---|---|
| 文件 | kebab-case，`.js` 小写 | `walk.js`、`hud-map.js` |
| 命名空间 | `SK` + 模块名（帕斯卡） | `SKScene`、`SKSceneShell`、`SKSceneWalk` |
| 构建函数 | 后缀 `Html`，返回字符串 | `roomHtml`、`propsHtml` |
| 判定函数 | `is*` / `can*` / `has*` | `isTypingTarget`、`walkable` |
| 纯数据表 | 全大写常量 | `ROOMS`、`LINKS`、`PROP` |
| 事件/交互出口 | 统一 `bind*` | `bind()`、`bindKeys()` |

### 3.2 文件头模板（**新文件必须写满七项**）

```js
/* =============================================================
 * <命名空间> · <一句话职责>（批 XXX · YYYY-MM-DD）
 * -------------------------------------------------------------
 * 职责：   只做这一件事，多一件就说明该拆
 * 不变量： 改这里必须守的 2~4 条（违反即红的那些）
 * 依赖：   只读谁（模块名，不写文件路径）
 * 状态：   自己拥有的可变状态；别人的状态一律只读
 * 对外：   导出的函数/常量（渲染器与门禁都只认这些）
 * 门禁：   守这个文件的是哪几条断言
 * ============================================================= */
```

### 3.3 文件大小红线

| 行数 | 判定 |
|---|---|
| ≤ 400 | 正常 |
| 400~800 | 允许，但头注释必须写清"为什么不再拆" |
| > 800 | **必须拆**（除派生物 `js/data/rules.js` 与归档 `_retired/`） |

## 四、状态归属表（拆分前先背下来）

| 状态 | 现位置 | 目标 owner | 谁能改 |
|---|---|---|---|
| `curRoom` 我在哪间房 | ui-scene | `scene/state.js` | walk（到达/跨房）、render（自动导航） |
| `walkState` 折线走动 | ui-scene | `scene/walk.js` | walk 独占 |
| `freePos` 自由行走落点 | ui-scene | `scene/walk.js` | walk 独占 |
| `panelOpen` 行动面板 | ui-scene | `scene/index.js` | index |
| `sig` 渲染指纹 | ui-scene | `scene/index.js` | index（其它模块置 null 表示"要重绘"） |
| `lastG/lastV` | ui-scene | `scene/index.js` | index |
| 聊天/日志滚动 | ui.js | `ui/chat.js` | chat |
| 面板表单值 | ui.js | `ui/panel.js` | panel |

> 拆分手法统一为：`scene/state.js` 暴露一个 `SKSceneState` 对象，
> 各模块 `const st = global.SKSceneState;` 读写**自己的**字段。禁止 `global.xxx = ...` 裸挂。

## 五、门禁配套（模块化的前置条件）

### 5.1 `tools/gate-src.cjs`（本批新增）

门禁不再写死文件路径，而是按**逻辑模块名**取源码：

```js
const { srcOf, bodyOf } = require('./gate-src.cjs');
const shell = srcOf('scene.shell');          // 归一到"剥注释后的源码"
bodyOf(shell, 'function roomHtml(S)');
```

板块映射写在 `gate-src.cjs` 的 `MODULES` 表里（**唯一真源**）。模块拆分时只改表，断言不动。

### 5.2 断言三条规矩（沿用 + 强化）

1. 判据落在**函数体内部**（`bodyOf`），不落在整个文件；
2. 判据落在**"那个动作那几行"**（先抠出小段再判）；
3. **改完断言必跑反向自检**（`npm run test:ship:selfcheck`），确认断言还能变红。

### 5.3 每个新模块必须有"存在性"断言

文件被加载（`SKShip`/`SKSceneShell` 之类命名空间存在）+ 主函数体有正确判据。
否则"文件在、没被加载"这类缺陷可以全绿（红线 9 的同源问题）。

## 六、素材规范（服务"美术素材对齐"）

### 6.1 两类目录，边界不可混

```
assets/
├── scene/     # 产品素材：必须登记许可、必须被引用或显式归档
│   ├── bg/ crew/ cozy/ rooms/ station/ characters/
│   └── CREDITS.md            ← 人工台账（出处/许可证/生成命令）
└── refs/      # 设计参考：不发布、不被 js/css 引用，登记出处即可
    ├── README.md             ← 登记表
    └── skeld-map-reference.* ← 地图设计参考（批 ART-0 新增）
```

### 6.2 命名与尺寸（改素材时逐条对齐）

| 类别 | 命名 | 尺寸 / 网格 | 锚点 |
|---|---|---|---|
| 瓦片 | `tiles/<kebab>.png` | 32×32 或 32×64 | 左上 |
| 家具 | `furniture/<kebab>.png` | 32 的倍数 | 左上（"坐"在图片底边） |
| 角色 | `crew/crew-NN.png` | 96×160 单帧，4 列 × 5 行 | 帧内可见内容居中偏下 |
| 内衬 | `bg/<kebab>-tile.png` | 无缝，4×4 格 | —— |
| 参考图 | `refs/<topic>-reference.(jpg\|md)` | 不限 | —— |

### 6.3 台账与门禁

- 产品素材：`assets/scene/CREDITS.md` 必须有一行；**未登记的素材不许上线**。
- 参考图：`assets/refs/README.md` 必须有一行；**不得被 `js/` 或 `css/` 引用**（不发版）。
- 机器台账：`node tools/asset-catalog.cjs --write` 生成 `assets/MANIFEST.json`
  （路径 / 尺寸 / sha256 / 许可条目 / 被引用次数），`npm run test:assets` 校验
  "磁盘 ↔ manifest 一致"。**换素材只改文件，重跑一次即可**。

### 6.4 「美术素材对齐」的验收口径（供下一个方向用）

1. 9 间房的地板/墙饰在 `space.js` 里逐间声明（已有 `floor` / `wall[]`）；
2. 每件家具的 `PROP` 尺寸与素材实际像素一致（`test:space` 的 S1/S2 已守）；
3. 角色帧内可见内容占比固定（`CREW_VIS_W/H`），换皮不改渲染；
4. 零引用素材清单可导出（`node tools/asset-catalog.cjs --unused`），要么接线、要么归档到 `_archive/`。
