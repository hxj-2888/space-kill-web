## 一、最值钱的部分：三条「注释写了、代码没做」

### 1.1 P0 · `anchorY` 从来没生效过

`js/ship-map.js` 的 `camera()` 先按 `anchorY` 算 `y`：

```js
let x = px - vw / 2, y = py - vh * ay;      // ← 按 anchorY 算
...
if (clampRect) {
  if (clampRect.h >= vh) y = 夹紧;
  else y = clampRect.y + (clampRect.h - vh) / 2;   // ← 又把它整个覆盖
}
```

房间 11 格 < 视窗 12 格 ⇒ **恒走 else 那一支** ⇒ `anchorY` 白传。
上一批的注释写着「面板展开时传 0.34，把我抬到画面上部」—— 那一行从落地起就没生效过。

**门禁为什么没报**：SH4 量的是「视窗整块落在房间内」，而"房间居中"**恰好满足**它。
一条断言守住了几何，却守不住"玩家要看见的那个点"。

> **教训**：断言要量**玩家要的东西**（"我"在不在屏幕上），不是量实现顺手产出的性质
> （"视窗在房间内"）。两者在多数情况下同向，但正是分歧的那一次出事。

### 1.2 P0 · 就算 anchorY 生效，viewBox 也不会跟着面板变

`render()` 只在 `key !== sig` 时写 `viewBox`，而 `key` 里只有 `panelOpen` 的**开关**、
没有"面板多高"。面板高度是 `renderStage` 填完表单**之后**才定的
（投票 15 个目标 ≈ 400px，只点一个按钮 ≈ 210px），于是：

```
面板从 210px 变 400px  ⇒ key 不变 ⇒ 不重建 ⇒ viewBox 停在旧值 ⇒ 人还是被盖
```

实测：修好 anchorY 后仍有 2/24 帧被压 38%~65%。

**修法**：新增 `applyCamera(mount)`，在 `render()` 收尾处**每次**调用（只改一个属性，
代价可忽略；重建 DOM 才是贵的）。SH15 逐行要求它是**裸调用**。

### 1.3 P0 · 「打开规则」有两份实现，一份渲染、一份不渲染

```js
// ui.js —— 首局自动弹出走这条
function openRules() { ov.classList.remove('hidden'); }        // ← 不渲染

// arena.js —— 主页铭牌走这条
rules.onclick = () => { ov.classList.remove('hidden'); renderRules(); };  // ← 渲染
```

首局 `render()` 里 `localStorage` 判首次 ⇒ 调 `ui.js` 的那条 ⇒ 浮层打开、正文永远是
index.html 的占位句「正在载入规则数据…」（实测 3 页签 / 0 张卡）。
关掉再点铭牌就正常（14 张卡）—— 所以**只有第一次进游戏的人会看到这个空页**。

**修法**：渲染收进 `openRules()`（唯一入口），`UI` 导出 `openRules/closeRules`，
`arena.js` 的 onclick 复用 `UI.openRules()`。

> **教训**：同一个动作有两份实现时，缺陷不会"一半出现"，而是**在特定的那条路上 100% 出现**，
> 而走另一条路的人（包括开发者自己复测时）永远看不到。

## 二、P1 两条：字读不出来的那种缺陷

### 2.1 房名被记录板压住

房名钉在房间左上角 `(o.x*TILE+14, o.y*TILE+34)`，`layoutClerk()` 也把记录板与小地图放左上
—— 实测「舰桥」与记录板文字重叠 **798px²**。
改为**右对齐钉在房间右上角**（`text-anchor="end"`，右边界留 0.45 格）。
让 SVG 那一份避开浮层，比让浮层记住"左上角还有字"更可靠（浮层已有小地图/席位/提交路径三重避让）。

### 2.2 侧门标签读不出

标签画在门矩形正中。左右门只有 0.7 格宽（39px），「查证室」三个字约 40px ⇒
字压在门框描边与门洞暗部上；且标签只有 `fill` 没有描边，落在浅色地板上几乎不可见。
改为按 side 把标签**推进房内 0.55 格**，CSS 加 `paint-order: stroke` + 深色描边。

> 这两条都只有**放大截图**能发现。门禁能守"元素在不在"，守不了"字读不读得出"。

## 三、★ 反向自检又抓到 3 条空转（本批最该记住的一节）

新写的 5 条断言先跑反向自检 —— **3 条改坏了仍然绿**：

```
✗ SH15 ⇒ 仍然绿   ← 判据只判「render 尾部有没有 applyCamera(mount)」，变异包进 if 之后子串还在
✗ SH17 ⇒ 仍然绿   ← 判据只判「body 里有没有 d.side === 'l'」，而门热区收边本来就有同一个 token
✗ SH18 ⇒ 仍然绿   ← 判据只判「body 里有没有 global.SKArena.renderRules」，兜底分支里还写着同一段
```

三条是**同一个错误**：判据落在"文件/函数里有没有这个 token"，而不是"正确的那一小段"。

上一批立的规矩是「B 组判据落在**函数体内**」。本批证明那**还不够** ——
落在函数体内也可能落在**另一个分支**上。

修法：
- **SH15** 逐行要求 `applyCamera` 是**裸调用**（行首直接是标识符，不许 `if/&&/?` 前缀）；
- **SH17** 先抠出"标签让位"那一段（`const off = TILE` 到 `data-side=`），再判左右两侧；
- **SH18** 只看**第一处** `renderRules`，且不许被 `false &&` 之类短路。

修完 **24/24 全部能变红**。

> **规矩（本批新增，写进 test-ship.cjs 文件头）**：
> **判据要落在"那个动作那几行"，不是"含这个 token 的任何地方"。**
> 判据的搜索范围越大，空转概率越高；最稳的写法是**先抠出正确的那一小段**再判。

## 八、已否决

- **把 `anchorY` 写死成 0.34**：实测过量 —— 夜里「我」本来站在房间底部，抬到 34% 会把
  桌子与整圈座位推出屏幕。必须按面板实测位置算。
- **用解析式反推 ay**：相机 y 对 ay 是分段函数（船体夹紧/房间夹紧/房间居中），
  "房间居中"那一支不满足 `camY = me.y − vh·ay`。第一版就是这么写错的：算出来
  "人本来就露着"，永远返回 0.5，症状与没改一模一样。**二分只依赖单调性，对任何分支都成立。**
- **让记录板记住"左上角有房名"**：浮层已有小地图/席位/提交路径三重避让，再加一条只会更容易漏。
- **放宽 U1F 的 emoji 判据**：本批注释里打了一个 `★`（U+2605）被 U1F 判红 —— 改注释，不改断言。
