## 四、⚠ 本批踩的坑：指纹漂移与静默集合口径

**现象**：清空 `PLACEHOLDER_STEPS`（原为 0.2/3.5 的静默集合）后，经典局指纹从 `fdd6415f` 漂到 `4d58fc04`。

**定位过程**（方法可复用）：
1. `stateSamples` 逐位相同 ⇒ AI 状态采样未变，怀疑面收窄到「非采样字段」；
2. 指纹行含 `log=` g.log.length ⇒ 首查日志增减；
3. 逐项中和 0.2/3.5/声明层/ROLE_SPEC（N=40 与 N=200）**均无变化** ⇒ 不是机制本身；
4. 源码级 A/B（自定义 vm 加载器替换 engine.js 单个条件）**一击定位**：`oldSkipRule + oldPH` 组合复现 `fdd6415f`。

**根因**：0.2/3.5 的候选角色（窃听者/猎手）在经典局根本不在场，「无决策者，整步跳过」纯属每夜重复的噪声——这既是玩家可见的缺陷，也是指纹漂移源。

**处置**：中途试过改为推导层判据（`ACT.sendersAt(step)` ∩ 本局在场），**实测与显式集合不逐位等价**（`9e939c90` ≠ `fdd6415f`）——「声明层无人」与「本局无人」在自动步位上不可混同。故回到显式登记，并在两处写明该口径的边界；另加 §23 断言「经典局不出现变体机制步位的跳过通知」把守，防再次回潮。

**教训**：清理「未实装机制」类豁免表时，须先确认豁免理由是否已随实装失效——本例中**理由未失效**（角色不在场仍是噪声），只是不再叫「占位步」。
